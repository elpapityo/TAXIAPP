# 現在地共有の通信・保存方式の見直し（未実装・未公開）

2026-11-01確認。目的は15秒更新・本人確認・操作端末確認を維持し、日報優先の無料運用を壊さないこと。現在の公開履歴GAS版5と日報原本/計算/印刷は対象外。今回実装したのは容量比較モデルであり、Cloudflareバックエンドはまだ実装していない。

## 比較の結論

既存GAS現在地候補を公開しても、13時間15秒間隔では1名の送信だけでGAS URL Fetch上限超過となる。Firestore RESTのbatchGet等でHTTPを減らしても、複数人の15秒更新を同じ個人GAS実行者で支える解決にはならない。

次の実装候補は、**現在地の6操作だけをCloudflare Worker + SQLite-backed Durable Objectの単一共有roomへ移す**方式。Googleログイン2系統・名前付きAuth・既存sender/preferencesのクライアント仕様は維持する。現在地をGASへ中継せず、Google本人確認と本人tokenによる日報資格/操作端末読取をWorker側で行う。現在地と設定・sender・資格コピーをDO内で扱い、日報へ書かない。履歴は既存GASを必要時だけ利用する。

これは選定候補で、無料運用を保証した採用決定ではない。新しい実行環境を増やすため、既存のアダプター境界を使い、別の画面や別の業務計算は作らない。

## 既存要件を守る境界

- Googleの2 ID tokenのオンライン検証を毎要求行い、同じGoogle subject/emailとactor GPS UIDを照合。JWT decodeのみの本人確認、token検証の5分キャッシュへ変更しない。
- 日報のusers/adminsを本人tokenで読み、現在地用の資格のみ最長5分保持。コピー期限は要求途中で延ばさない。既存linkの定期呼出は現在地から外す設計が必要。現linkを残すと10名で1,640回×13=21,320 URL Fetchとなり、GAS上限問題が再発する。
- writerの送信/取得/停止/設定変更は書込直前に日報deviceSessionsを本人tokenで照合。操作権の取得・切替は行わない。この要件を緩めて回数を合わせない。日報と別ストア間の原子的トランザクションまでは保証できず、これは現GAS同様の限界。
- DOではpublic既定false、操作ID/改訂CAS、120秒sender排他、非公開の座標消去/解放を同一状態更新として維持。非同期の外部確認中に状態が変わった場合はcommit前に改訂を再確認する。
- 一覧は有効資格・公開・営業中・sender一致・5分以内の座標だけを返す。本人が隠した位置、Google subject/email/日報UID/端末IDを返さない。全一覧をHTTPキャッシュしない。
- 1ユーザーの状態を1行へ統合し、最新座標だけ上書きする候補。時系列の位置履歴をDOへ無制限追加しない。旧Firestore/GAS候補を消さず、切替時に未同期公開操作を保護する。
- 既存のtext/plain本文POSTを使い、Origin許可一覧・本文上限・エラー時の送信停止を実装する。CORSは認証の代用にしない。text/plainにするだけで無料枠保証とも扱わない。

scripts/gps-presence-capacity.jsのestimateEdgeCandidateとgps-presence-edge-capacity-20261101.jsonが再生成可能な根拠。既存GAS見積りは変更していない。上限抵触が無くてもproductionReadyは常にfalseで、実運用可とは返さない。
