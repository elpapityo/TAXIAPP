# Firebase日報ゴミ箱：安全な段階実装（2026-10-21）

## 目標と現状
本人が選択した日報1件を**サーバー上でゴミ箱に移動**し、必要なら復元できる。30日経過後は**日報本文・売上・GPSなどの原本をサーバーから完全削除**する。削除した日報がPC・スマホの同期で復活しないことが必須。

**本PRではゴミ箱のFirestoreクライアント処理の試作と、合成データの回帰テストまで。実アプリの削除ボタンには接続していない。Firestoreルール、本番DB、Google Sheets、認証設定は変更していない。**

前提PR：#113（管理者Firestore本人照合）、#110（未同期ローカル保護）。仕様：#105・#111・#112。

## 保存構造（提案）
本人UIDの下に置き、他ユーザーとは絶対に共有しない。

| パス | 用途 | 30日後の扱い |
|---|---|---|
| `privateDuties/{uid}/shifts/{shiftId}` | 通常日報の原本 | ゴミ箱移動時にトランザクション内で消去 |
| `privateDuties/{uid}/trash/{shiftId}` | 退避した日報全文、元の更新番号、期限 | **30日後にFirestore TTL/信頼できるサーバー処理で消去**（未設定・未検証） |
| `privateDuties/{uid}/tombstones/{shiftId}` | IDの削除状態・最終更新番号・世代（売上・GPSなし） | **旧端末の再作成を拒否するため最小マーカーは残す**。日報原本は持たない |

### ゴミ箱移動（1件ずつ）
1. 認証UID・その端末の編集セッション、対象ID・更新番号、ユーザーの明示的確認をチェック。
2. Firestoreトランザクション内で同じUIDの原本・ゴミ箱・墓標を読み、原本が存在し版番号が同じで、まだゴミ箱にないことを確認。
3. ゴミ箱へ原本を退避し、墓標を「deleted」にし、通常日報の原本を削除。**3操作の全成功/全失敗**を担保。
4. サーバーでの確定後に端末の一覧・集計・印刷から除外する（UI・同期側の対応は**今後実装**）。通信失敗時は消えたと表示しない。
5. 出庫中・編集中の日報や複数件まとめ削除は今回許可しない（運用仕様の精査が必要）。

### 復元
本人の明示的確認後、トランザクション内で原本が存在せず、ゴミ箱と墓標の世代・元の更新番号が一致し、期限内であることを検証。新しい更新番号で原本を復活させ、墓標を「active」にしゴミ箱全文を削除する。既存IDへの上書きは**しない**。別IDとの乗務時間重複もUIで警告すべき（未実装）。

### 完全削除（**無料運用優先**）
**重要：Firebase公式のFirestore料金表では、マネージドTTL削除は無料枠の対象外で、利用には課金設定が必要。** 本アプリでは利用者が無料運用を希望しているため、TTLを無断で有効化しない。

- **第一候補（無料枠内での利用を目指す）：** ゴミ箱移動から30日経過後、本人が次にアプリへログインして編集権を持つタイミングで `purgeExpired()` を呼び、サーバーの期限切れゴミ箱原本を削除する。Firestore標準の読み取り・書き込み・削除回数の無料枠内なら費用は発生しないが、枠を超えると課金条件による。**アプリに誰もアクセスしない期間は期限超過データが残る**。
- **第二候補（有料・要事前承認）：** Firestore TTLにより期限到来後の自動削除を依頼する。TTL削除は無料枠外で課金設定が必要。実際の削除は即時ではなく、通常は期限後24時間以内の遅延があるため「30日ちょうどで消える」とは約束しない。
- **本PRの試作は `purgeExpired()` のユニットテストまで。** ユーザー画面・ログイン時の自動呼出・Firestore Rules・TTL設定には未接続。
- いずれも本人UID、サーバーでの期限照合、現行編集セッション、墓標の維持を必須にする。
- Firebase公式料金資料： https://firebase.google.com/docs/firestore/pricing
- TTL挙動の資料： https://firebase.google.com/docs/firestore/ttl

- Firestore TTLは別途管理者の本番設定が必要であり、**今回設定していない**。TTLの削除時刻には遅延があり得るため、単に期限フィールドを置いただけで「30日で必ず削除済み」と報告しない。
- 自動TTLを選ぶ場合だけ `trash.expiresAt` のTTL設定と課金影響を別途確認する。無料案は次回ログインでの期限切れ整理。
- 法令・税務上の保存義務がある日報は、試験用の日報とは区別して保持・バックアップ要件を確認する。
- 墓標は売上・GPS・個人の明細を保持しないが、旧端末の再アップロード防止のため残る。**データの完全な無痕跡化とは異なる**。保存期間は別途判断する。

## **現在のFirestoreルールでは動かない**
`firestore.rules` の現在の `shifts/{shiftId}` は `allow delete: if false` であり、`trash`・`tombstones` にアクセス権がない。**本番環境のルールは変更しないこと**。

**安全な公開に必要なルール要件：**
1. `request.auth.uid == uid` ＆既存 `admins`/有効 `users` ＆**サーバーで確認された現行編集セッション**だけがゴミ箱移動・復元可能。他人/旧編集端末/未承認/閲覧専用を拒否。
2. 原本・ゴミ箱・墓標を **同一トランザクションの `getAfter()` / `existsAfter()` 等で整合確認**。**原本だけの削除、原本退避なしの削除、墓標なしの削除、復元なしの墓標active化を拒否**する。実際に使うRules APIと評価回数上限をEmulatorでテストする。
3. 墓標が「deleted」であるIDは `shifts` の **create、update、旧端末からの初期アップロードを拒否**する。復元時のみ、同時に墓標をactiveへ変更する**許可された原本復元トランザクション**を認める。
4. 墓標やゴミ箱の任意編集・原本差替・勝手な期限延長・他人のゴミ箱参照/復元を禁止する。
5. `expiresAt` は信頼できる基準時刻を中心に30日以内へ固定し、クライアント時計や改変による無期限保管を許さない。
6. 本番の既存ルールを上書きせず、差分・バックアップ・ロールバック案を作成し、**EmulatorでUID、古いセッション、CAS、再同期、期限、TTL、復元、重複ケースの拒否/許可を検証**してから、事前承認で本番公開。

## 同期復活防止の検証コード（今回追加）
- `firebase-duty-trash.js` に `readDeletionMarkers(shiftIds)` を追加。本人UIDの `tombstones/{shiftId}` を**各IDごとにサーバー取得**し、欠損も含めて全件取得しなければ照合失敗とする。UIDの途中変更、通信失敗、不正な形式、重複IDは拒否。
- `planReconciliation({uid,serverUid,localShifts,serverShifts,markerStates,markersComplete})` で**端末に残る日報の再送信可否を分類**する。削除済みマーカーは `protect-local-copy`、同ID内容違いは `review-difference`、新規候補も `candidate-new` として扱い、すべて `uploadAuthorized:false` を返す。**どの判定結果もアップロード・削除を自動許可しない**。
- 復元後に通常の保存で更新番号が増えても、墓標が `active` であれば次のゴミ箱移動を行えるよう、更新番号は移動対象原本とユーザー確認の期待版で検証する。古い墓標の版番号だけを根拠に誤拒否しない。
- 未入庫・精算中の日報は現段階のゴミ箱移動を拒否する。日報の内容に対する操作中の編集セッション変化も拒否。
- `tests/firebase-duty-trash.test.js` に **削除→旧端末のローカル保持→再アップロード候補の抑止判定**、欠損マーカー、他UID、復元後編集→再削除、編集中拒否、通信中のUID変更を追加。
- この判定コードは現時点の `bidirectional-sync.js` や `account-diary-store.js` には**接続していない**。現在の本番では依然として日報が復活する可能性がある。新旧クライアントの安全を担保するにはFirestore Rulesの `deleted` マーカー確認と同期UIへの結合が別途必要。

## 今回の試作コード
`firebase-duty-trash.js` は `TAXIAPP_DUTY_TRASH.create()` を提供。本人UIDに `bind()` し、`move({shiftId,expectedRevision,confirmed:true})`、`list()`、`restore({shiftId,confirmed:true})`、`purgeExpired({max:20})` を試験可能。**未実装のUIやRules公開を迂回して本番で呼び出さない**。

`tests/firebase-duty-trash.test.js` はモックFirestoreを使って版競合、本人の確認、再削除、復元、期限、UID変更、読み取り専用拒否、旧端末の再送信候補抑止などを検証する。モックテストはセキュリティルール実機試験の代わりにはならない。

## 本番切替までの残作業
- 既存 `account-diary-store.js` と双方向同期の通常クライアント・旧端末で **墓標のある日報が再作成されないこと**を本物のRulesで検証。
- 削除済み日報をローカルIndexedDBの未同期データと見なして**自動復活しない**同期統合。PR #110の安全保護/競合確認との結合。
- 利用者の「日報一覧から選ぶ → ゴミ箱 → 復元」UI、同ID/時間重複確認、各日報の保存状態を可視化。
- Firebase Rules公開・本番データの選別削除・TTL設定、旧Google原本整理・印刷出力は**別々に承認**が必要。新規有料サービス導入時も承認。
