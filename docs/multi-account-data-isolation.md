# TAXIAPP 利用者別の日報保存方式（v0.3.111）

## 2026年10月24日：Googleログインによる利用者の自動登録（開発版・本番未反映）

- 本人が初めてGoogleでログインし、**認証方法がGoogleかつメール確認済み**で、管理者でも既存利用者でもない場合に限り、「オプチャネーム」を必須入力してから本人の `users/{uid}` に `status:'active'`、`openChatName`、サーバー時刻 `registeredAt` を**同一ドキュメントで同時登録**する。名前未入力・不正入力では利用者レコードを作らず、日報編集を開放しない。書込み後はサーバーから本人UID・状態・名前を読み戻して確認する。
- オプチャネームは本人による自己申告であり、LINEオープンチャットの所属や一致を自動検証するものではない。名前の重複は許可し、後からユーザー自身が勝手に既存プロフィールを書き換える操作は今回追加しない。旧承認済み利用者・管理者のログインは名前未登録でも維持する。
- Firestoreルールは**本人UIDの新規作成のみ**許可。オプチャネームは必須文字列（1〜32文字・空白のみ禁止）。別人への登録、管理者権限の作成、既存の利用者情報の更新・削除、停止中・保留中アカウントの再有効化は許可しない。
- **重要：このルールを本番公開すると、Googleアカウントを持つ不特定の利用者が登録可能になる。** LINEオープンチャットの参加者に限定されない。利用者数・保存量・Firebase課金の増加を防ぐ登録人数制限や招待制は今回含まれない。
- GitHubのコード変更やPR作成のみでは本番Firestoreルールは変わらない。**本番のルール反映、認証設定変更、PRのmain統合・正式公開には別途明示承認が必要。**
- 公開前にFirebase Emulatorで「本人のGoogle認証＋オプチャネームで新規登録成功／空欄・空白名・他UID・管理者権限・更新・停止中の再登録は失敗」、実本番に影響しない試験アカウントで「ログイン後の名前入力・初回・再ログイン・端末切替・本人原本保存・他人へのアクセス拒否」を確認する。
- 自動登録が拒否された場合は**編集を開放しない**。既存管理者のGoogle保存、本人日報の計算・印刷・端末原本を変更しない。


## 利用者ごとの保存先

| 利用区分 | 営業日報の本体 | 端末の一時保存 | 設定 |
|---|---|---|---|
| 既存の管理者 | これまでのGoogle Apps Script / Googleスプレッドシート | 既存の `taxiapp` IndexedDBキー（変更なし） | Firebase `accountSettings/{uid}` |
| 承認済み一般利用者 | Firebase Firestore `privateDuties/{uid}/shifts/{shiftId}` | `taxiapp-account-state-v1-{uid}` IndexedDBキー | Firebase `accountSettings/{uid}` |
| 未ログイン・未承認 | 閲覧・編集不可 | アカウント専用の営業記録は開かない | なし |

UIDはFirebase Authenticationの認証済みUIDです。アプリはログイン成功後にサーバーの `admins/{uid}.enabled` / `users/{uid}.status=active` を確認してから保存先を選びます。

- 一般利用者の保存先は自動的に自分専用となり、**管理者のGoogleスプレッドシートは使用しません**。
- Google Apps Scriptの秘密キー、URL、日報印刷画面は一般利用者へ提供しません。端末に以前から残っていたGoogle接続情報を一般利用者のデータとして扱いません。
- 同じ乗務IDが違う利用者に存在しても、別のFirestoreパスなので混ざりません。
- 旧管理者の日報、既存の印刷帳票、料金計算は移行・変更しません。
- 新ユーザーの端末のローカル保存は認証UID別です。ログイン前に以前のユーザーの日報を表示しません。
- 同じアカウントで端末を変える場合、サーバーに確定した操作権を確認し、Firestoreに保存済みの乗務を読み込んでから編集します。
- Firestoreの各乗務は更新番号を使った比較・置換で同期します。衝突する更新を無条件に上書きしません。
- 一般利用者の乗務を削除するサーバーAPIは用意していません（削除ルール拒否）。将来のアーカイブや復元は別途設計します。

## 【本番利用前に必須】Firestore権限ルールの反映

リポジトリの `firestore.rules` の更新は**Firebase本番のアクセス制御を自動更新しません**。Firebase管理者がプロジェクト `taxiapp-2b6bd` の Firestore Database → ルールへ、リポジトリ内の**完全な最新版** `firestore.rules` を反映・公開してください。既存の `admins`、`users`、`deviceSessions`、`accountSettings` のルールも維持するため、該当ルールだけを継ぎ足すのでなくファイル全体を使用してください。

同じことをCLIで行う場合は管理者の権限とFirebase CLIが必要です。Firebase Consoleでルールを公開したときの実際の反映結果を確認してください。

**ルール反映前は新規一般利用者の読み込みが permission-denied となり、編集禁止のままです。** 安全のため自動的に旧Googleシートへ切り替えないでください。

## 【本番利用前に必須】2アカウント実機検証

1. 既存管理者：旧日報と印刷シートが従来どおり使えることを確認する。
2. 有効な一般ユーザーA：ログインして新しい乗務を入力し、Firestore `privateDuties/A/shifts` にだけ保存されることを確認。
3. 一般ユーザーB：ログインした際Aの乗務を一切表示せず、別の `privateDuties/B/shifts` に保存されることを確認。
4. AとBが同じ乗務IDを持っても混同しないことを確認。
5. Aで保存したあと、別端末のAで取得・編集できることと旧端末の操作権が停止することを確認。
6. Firestoreのルール検証で、Aの認証ではBの原本が読めず書けず削除できないことを確認。
7. 通信エラーでは編集が開放されず、復旧後に正しい本人の記録が取得されることを確認。

これらを完了するまで**一般利用者への本番配布は保留**にしてください。管理者の既存記録もバックアップしてください。

## その他の仕様と今後

- 原本1乗務につき最大60記録、JSONサイズ最大850KB。大きなGPS走行履歴は原本へ格納せず、将来専用ストレージを使用する方針です。
- 位置共有やランキング、会社別テンプレートは利用者別日報とは別機能です。初期値非公開・本人の明示的同意を前提にします。
- 管理者用のGoogle Sheet保存キーは従来の端末保存方式のままです。同じブラウザプロファイルを他人へ共用させないでください。アカウント切替時に画面・通常APIから旧日報へアクセスできないことと、OSレベルの完全な情報隔離は別問題です。
- 旧運用ではGoogleログイン後も管理者による `users/{uid}` 有効化が必要でした。上記2026年10月24日の自動登録方式は開発ブランチの変更であり、本番ルールを承認・反映するまで旧運用を維持します。
