# TAXIAPP アプリ開発16・二人で行う確認手順（2026-10-22）

> **紙の補助簿2ページを実際に印刷する試験は不要（対象外）**。目的は出庫→保存→同期→入庫→必要時の過去日報修正→PCの乗務選択→**既存4印刷元の内容一致まで**を確認すること。既存の営業データは一切使用・移行・削除しない。

## 作業中の前提

- 対象はPR #119のドラフト実装。GitHub Pagesの通常URL `https://elpapityo.github.io/TAXIAPP/` は `main` の公開版で、PR #119の検証画面ではない。開発版URLを未確認のまま提示しない。
- `google-apps-script/Code.gs` には現行本番の `TAXIAPP_SHEET_ID` が記されている。**開発版GASをそのまま実行すると既存帳票を対象にする危険がある**。隔離テストでは必ず **テスト専用に作成したスプレッドシートID**へ差し替え、実ファイルの編集・公開はしない。
- 最初はGitHub Actionsと合成データで実装を確認。実Googleの認証・Firestoreからの取得や本番GAS再デプロイは未承認なので行わない。接続試験に必要なアカウント/IAM/OAuth変更は事前承認を得る。
- 管理者の正式なFirestore原本切替 `ADMIN_FIRESTORE_CUTOVER_ENABLED=false` を維持する。旧Google原本は現行のまま保持し、PR #115のゴミ箱整理や本番ルール変更は扱わない。

## 最初の確認（ユーザー操作不要）

1. GitHub PR #119の最新HEADと未統合状態を確認。
2. `tests/firestore-to-existing-print-sheets.test.js` で、同一ID・異なる更新番号の再取込／同版繰返し／行増減／第三者書込／書込み失敗後の復旧を合成確認。
3. `tests/firestore-print-selected-confirm.test.js` で、PCのB15/B17/C17・本人UID・原本との全明細一致、改版中断を合成確認。
4. Node・GPS/HTML・Chrome営業データ保護の既存テストを通し、失敗時は実コードの原因を修正する。

## 次に二人で確認する手順（テスト専用環境が準備できた場合）

1. 本番とは別のテスト用アプリURLと、本番営業記録を含まない専用Firestore UID／合成日報を用意。実UID・本番権限・既存原本をテストに流用しない。
2. 本番のGoogle補助簿を直接操作せず、隔離されたテスト用スプレッドシートで **4つの既存印刷元相当の列構造**を確認。実Google接続設定は個別の承認・バックアップ・切戻し手順を用意してから行う。
3. 合成乗務1件を出庫→営業記録→支払確定→入庫の順で保存し、Firestoreの本人原本ID／更新番号／内容を読み戻し一致確認。
4. PCで合成乗務IDを明示的に選択。4印刷元の乗務ID・件数・決済内訳・金額を確認（**紙印刷しない**）。
5. その合成乗務の乗車地だけを修正し、更新番号が増えたことを確認。同じIDで再取込し、4印刷元の内容だけが更新されたこと、旧原本・数式・ほかのIDが不変であることを確認。
6. 同じ版を再取込して重複なしを確認。次に合成の支払内訳行数を増減し、最後の行ブロックのみ安全に更新されることを確認。
7. 途中通信失敗や意図した版違いを合成環境で試し、旧データ保持または安全停止と必要な復旧メッセージを確認。**他の乗務の後ろにある行の増加は自動操作せず停止**することを確認。

## 結果の区分

- 「開発版コードで合成テスト成功」は実機完了／本番利用可能とは別。
- 「PC印刷元の実シート転送成功」は「紙の補助簿2ページ印刷」ではない。紙印刷の試験は今回の完了条件に含めない。
- 実営業データの移行・削除、Firestore Rules/IAM/OAuthの本番変更、GAS公開版の再デプロイ、本番保存先切替、PR統合はいずれも別途承認が必要。
