# 現在地共有のGAS接続候補（未公開・共有停止を維持）

## 実装した範囲

公開済みの本人/管理者GPS履歴はGAS版5。今回の候補は既存履歴を変更せず、現在地用の6操作を追加する別生成の版6（gps-v6-presence）。本番編集欄/main/HTML読込/停止フラグは変更していない。

- Presence.gs / Code.presence-candidate.gs：送信元取得、位置送信、停止、本人の公開設定取得/CAS更新、共有車両一覧。GPSプロジェクトのgpsSenderSessions/gpsSharePrefs/gpsPresenceだけに書く。
- gps-presence-gas-adapter.js：日報UIDとGPS UIDを区別し、既存の2 token本文POSTと本人切替ガードを再利用。初期化で通信/測位を始めない。送信元保存確認、設定の操作ID/改訂番号、位置保存時刻を照合する。送る位置項目を限定し、任意の名前/UID/Firestore sentinelを送信しない。
- gps-presence-sender.js：既存の120秒送信元/90秒更新の排他制御にremote経路を追加。従来のFirestore経路は保持。GAS指定でFirestoreへ代替接続しない。日報の操作端末を自動取得せず、session.canWrite/sessionIdを参照する。どちらかのAuth利用者オブジェクト/操作端末IDの切替でcanTrack=false。
- gps-sharing-preferences.jsの既存CASをアダプターに接続できる。非公開の設定更新は、設定の改訂と表示用座標消去・送信元解放を同じGPSトランザクションで行う。端末の未同期公開操作は既存仕組みで保持する。

## サーバー条件

Googleで検証した同じ本人の2プロジェクトID tokenとactorUid=GPS UIDを毎回確認。現在地だけは、承認・公開済み本人連携が発行する最長5分のGPS資格コピーを使う。停止/資格変更は最大5分以内に反映し、瞬時失効とは扱わない。Googleトークンのオンライン検証は毎回維持。送信/停止/設定変更/送信元取得では、commit直前に日報の現在deviceSessionsを1回読んでwriterSessionIdを照合する。操作端末を新規作成/取得/切替しない。開始/commit前/応答前はGPSコピーの状態/本人対応/絶対期限を再確認し、途中で更新されても当該要求の期限を延長しない。履歴/管理者APIの毎回の日報資格確認は変更しない。

送信元は同じ日報操作端末内で120秒の排他。同じwriterの別senderは有効期限まで待機。現在の日報操作端末が変わった場合のみ新writerから取り直せる。旧senderの送信/停止は他のsenderの位置を消せない。

公開設定は操作IDとbaseRevisionでCAS。未確認の公開設定を暗黙の公開として扱わない。本人が選ぶ非公開は設定/表示用座標消去/送信元解放を原子的に行う。保存後も非公開と座標nullを読む。

共有一覧は5分以内の候補を最大100件（上限超過をtruncatedで明示）。公開/営業中、GPS側の有効な資格、現在の公開設定/送信元一致を確認してから、表示名/状態/精度/座標/更新時刻だけ返す。他者の日報原本/日報UID/Google subject/メール/送信元IDを返さない。停止/資格失効の伝播はGPSの期限付き資格に依存し、全端末への瞬時反映を保証しない。受信後も既存presenceViewで5分経過を非表示にする。

## 検証結果

Node44件成功（既存送信元/共有認証/停止設定＋新アダプター）。初期化0通信、閲覧専用の送信元取得禁止、UID分離、既存公開CAS、送信/停止、誤送信元/不正時刻、本人/操作端末切替の送信停止、5分非表示を確認。

実Firestore REST Emulator15件成功。従前履歴/管理者11件に、現在地の排他/公開CAS/非公開時の原子的座標消去/旧writer停止拒否/期限後交代/不正点/5分非表示、既存クライアント→GAS VM→実RESTの結合を追加。Google認証と日報資格/端末は合成。初回の追加試験では前試験と同じUIDの公開設定が残り、CASが想定どおり拒否。試験UIDを分離し初期保存応答も検査して成功した。保護条件は緩めていない。

## まだ公開・有効化しない理由

現在のgps-sharing-test.jsは旧Firestore直結UI。新アダプターをHTMLへ読み込んでおらず、描画/測位/営業状態を含む実画面への接続は未実装。既存presenceViewへ渡せる表示形式と、既存送信元/設定の経路までを今回実装した。全画面のGAS化完了とは扱わない。

日報側の負荷対策として、現在地の操作は最長5分の既存資格コピーへ接続した。commit直前の操作端末1文書だけを日報側から読み、送信1操作の最大11読取を1読取へ、一覧/本人公開設定の取得は6読取から0読取へ減らした（追加link/再送は別）。実REST試験で回数を検査し、旧writerのcommit拒否・期限切れ/停止コピー/不正UID対応/不正な長期期限の拒否も確認。利用資格の停止はコピー期限まで遅れ得る。Googleトークン検証・履歴/管理者の現行資格確認は変えていない。

ただしGAS自体の制約が残る。[Apps Script公式割当](https://developers.google.com/apps-script/guides/services/quotas)では個人Gmail実行者のURL Fetchは20,000回/日。[Firestore公式割当](https://firebase.google.com/docs/firestore/quotas)は読取50,000/日・書込20,000/日（2026-11-01確認）。上限は変更され得る。GASは実行者に集中し、利用者ごとに20,000回が追加されるわけではない。

現候補の成功送信経路は、Googleの2 token検証2回、GPS側HTTP10回、日報の操作端末1回の合計13 URL Fetch。これは実RESTでGPS HTTPと日報読取を数えて試算モデルと照合した。13時間ずっと15秒間隔で送ると3,120送信、送信処理だけで40,560 URL Fetchになり、個人Gmailの20,000回を上回る。日報側読取を減らしただけではこの条件を満たせない。送信元更新/一覧/資格更新/再送/履歴はさらに別であり、単独GASで複数人の高頻度共有が完了したと扱わない。

`scripts/gps-presence-capacity.js` と `docs/gps-presence-capacity-20261101.json` に、1/2/10名、13時間、送信15/90秒・一覧60秒の静的モデルを保存。実課金の測定やクォータ予約ではない。停止/公開切替/再送/実日報・履歴/インデックス等を含まず、実利用の保証はしない。このモデルで全てのケースがURL Fetch上限を超えたため、現在地候補を公開/有効化しない。

次は現在地共有の保存/認証/通信方式そのものを見直す必要がある。決定済み15秒更新を勝手に遅くせず、無料プランのために認証を無効化せず、課金へ変更しない。現UIの接続だけ先に進めても上限問題は解消しない。GAS更新の承認自体は本人から委任済みであり、本件は承認待ちによる停止ではない。

## 維持するもの

公開GAS版5、mainの停止設定、Spark/GPS全拒否、本人/管理者履歴の実成功、日報原本/既存計算/印刷を保持。実際の測位/位置共有/定期整理を開始しない。実Google/GAS/IAM/2名/端末/13時間量はこの現在地候補では未検証。
