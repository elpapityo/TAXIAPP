# TAXIAPP 今後の統一保存・印刷専用シート・ゴミ箱仕様（2026-10-21）

## 位置付け
**利用者とChatGPTで決定した目標仕様**。**現行mainには未実装・本番未反映**。既存コードと異なる箇所は段階的に切り替え、営業データ・スプレッドシート・印刷機能は切替の完了まで現状維持する。
参照：Issue #105（保存先統一）、Issue #111（重複整理）、PR #110（未同期日報保護・承認制の試作）。
この仕様は、従来の「管理者はSheets原本／一般利用者はFirestore原本」という運用に優先する**将来の決定方針**であり、既存データをすぐ移動・削除してよいという承認ではない。

## 1. 正式なデータの保存先
- **管理者本人も含め、すべての承認済み利用者**の日報原本（乗務、売上、明細、決済、高速、GPSなど）は **Firebase Firestore `privateDuties/{uid}/shifts/{shiftId}`** に保存する。
- 管理者権限は印刷・運用管理を許可する役割。管理者でも他者の原本は無条件に参照できない。日報の所有権は認証UIDで分離する。
- HTMLスマホ・PC・Androidは本人のFirestore原本を双方向同期。IndexedDBは本人別のオフライン一時保存・復旧用として残す。
- ネットワーク障害中の未同期レコード、競合、別端末の操作権、CAS更新番号を守り、クラウドの空配列で未同期の端末日報を上書きしない。
- **Google Sheetsを営業日報原本の保存先にしない**。SheetsからFirestoreへの逆同期も実施しない。
- 上記の目標と違い、**現状のmainでは管理者は旧Google Sheets・一般利用者だけFirestore** である。これを現時点で稼働中の統一構成と誤表記しない。

## 2. Googleスプレッドシートは印刷専用
- 管理者が自分のFirestore保存済み日報から印刷対象を選び、必要な日報1件の**印刷用派生データだけ**を既存Apps Script経由でGoogle Sheetsの印刷帳票へ一方向反映する。
- 印刷対象の履歴・原本をSheetsに蓄積して新たな正本を作らない。印刷用作業領域への一時反映は許容するが、印刷の再実行はFirebase原本を基準とし、印刷用派生データからFirebaseの原本を変更しない。
- 既存の帳票レイアウト、印刷マクロ、書式、式、紙のページ分け、ドロップダウンなどを保護する。どの印刷用保存表を維持・更新・消去できるかは実際のシートの式・参照関係を検査して決める。
- 一般利用者には管理者のSheets URL・アクセスキー・印刷権限を渡さない。
- 印刷データの更新失敗はエラーを表示し、最後の印刷版を新しいと誤認させない。

## 3. 日報の削除・ゴミ箱・完全削除
ユーザーが一覧から**対象日報を選択**してゴミ箱へ移動する。**端末だけの削除で完了扱いにしない**。
1. 日付・出庫/入庫・営業件数・売上・乗務ID・同期状態を提示し、対象と本人の確認を必須にする。
2. Firebase原本の状態を現在の更新番号で検証し、削除権限のある本人の編集端末セッションのみゴミ箱移動可。移動後はすべての端末で通常一覧・同期・売上・印刷対象から除外。確認前/通信失敗なら削除済みにしない。
3. ゴミ箱画面から保管期間内に**復元**できる。復元前に同IDの競合・時間重複を確認し、本人の許可なく自動上書きしない。
4. 保管期間は**30日を仮の初期案**とする（最終設定・法令上の保管義務は確認）。期間後は検証済みのサーバー側処理で**実際の営業原本を完全削除**する。Firestoreの非表示だけでは要望を満たさない。必要ならユーザーが「完全削除」を別確認の上で要求できる方式も検討する。
5. 本体を完全削除したあとも、古い端末が同じ乗務IDを再アップロードして復活させないため、**削除済み識別子（墓標）または端末同期世代の照合**を実装・テストする。原本そのものを永続保持しない。
6. 削除・競合時の保護コピー／印刷用派生データ／復元データの保持期限・消去対象も一覧化する。保護コピーが永遠にサーバーに残らない設計が必要。一方、消去前の利用者ダウンロード済みバックアップや法定保存対象は別管理。
7. 特に**テスト日報を選択して消せること**、削除後の同期で復活しないこと、誤操作後の復元、ゴミ箱期限後の完全消去を受入試験に含める。

### 重複・競合
- 日報IDが同じで本文が異なる「版競合」と、**IDは異なるが乗務時間が重なる「時間重複」**の両方を検出・警告する。
- 候補を自動的に削除しない。比較して「残す・編集する・ゴミ箱へ移す・保留」を利用者が選択する。
- 承認を伴う上書きは、両方の原本の退避・復旧可能性検証と再取得CAS確認が必須。保護に失敗したら書換えを拒否。

## 4. 既存の管理者日報の移行（実データへの操作は別途承認）
1. 現行管理者のIndexedDB、Apps Script/Google Sheets日報原本と既存の印刷設定を読み取り専用で調査・バックアップする。旧資料・印刷元はこの時点で削除しない。
2. 乗務ID・日時・乗車件数・売上・高速・GPS/距離・手数料などの原本と突合し、同じ期間の重複も表示する。
3. 管理者本人が **残す日報を選択**。特に現在端末で「必要なのは2件、同期で5件程度に戻る」という報告があるため、不要なテスト日報を機械的に全部移行しない。
4. **同じUIDのFirestore試験データへ段階的にコピー**し、1件ずつ読み戻し照合。対象数・売上・明細と従来印刷を比較。原本同士の競合は保留。
5. Firebase原本 → 既存Sheets印刷用一方向出力が実際に機能することを確認後、管理者本人の明示的承認で日報保存先の切替を行う。
6. 切替後の旧Google Sheets保存原本の片付けは、印刷機能に影響しないこととバックアップの保持期間を確認した**別個の削除承認**を必要とする。稼働中に自動消去しない。

## 5. 実装への影響（確認済みの現在のコード）
- `index.html`: `memberDiary()` / `legacyDiary()`、`scopedStorageKey()`、`switchAccountScope()`、`onWriterSnapshot`、`syncUI` の接続先・パケット生成、`renderPrint`、`renderSheetTargetSettings`、`deleteWholeShift()` を変更対象として調査。
- `account-diary-store.js`: 管理者をFirestore保存から除外している分岐を変更する必要あり。新規追加・版照合とゴミ箱移動・復元APIは別途設計。
- `firestore.rules`: 現状 `privateDuties/{uid}/shifts/{shiftId}` は `delete: false`、書込み構造は5項目のみ。ゴミ箱状態・削除済みマーカー・期限付き完全削除に対応するルールとバックエンドを**Emulatorで検証した上で**別途承認して公開する。
- `google-apps-script/Code.gs`: 現状 `syncList/syncGet/syncPut` はSheetsの保存原本を利用。Firebaseから印刷用データだけ反映するAPI/経路を別途追加・検証し、既存帳票を傷つけない。
- PR #110 にて一般利用者の未同期日報保護・競合許可制を開発中。**統一保存・ゴミ箱完全削除の動作が検証済みという意味ではない。**

## 6. 検証・本番切替のゲート
- 本番Firebaseルール公開・本番データ移行・Apps Script本番更新・権限変更・実データ削除は**それぞれ実施前に承認**を得る。
- Emulatorで UID本人・別UID・管理者・旧編集端末・古いrevision・未承認・読取専用端末の許可/拒否試験を行う。
- 合成データで削除→同期後に復活しない→復元→再削除→期限切れ完全削除→旧端末同期まで再現する。
- 現行Google Sheetsの日報・印刷の動作比較、Android/PC/ブラウザでの出庫・入庫・売上・印刷の実機試験を完了するまで切替しない。
- 稼働中の本番データには今回一切変更を加えない。

**進行状態:** ここに記載した統一保存・印刷専用化・ゴミ箱・完全削除は、仕様決定と移行の計画段階。実装済みや動作確認済みとはしない。
