# TAXIAPP アカウント登録・ログイン決定仕様と実装状況（2026-10-25）

## 決定済みの仕様
- 既存のTAXIAPP URLを維持。初回アクセスは「新規登録」「ログイン」を案内する。
- 登録済みも、別Googleアカウントでのログイン、新規Googleアカウントで登録、ログアウト、現在のアカウント確認が可能。
- **Googleアカウント1件につき登録1件、オプチャネーム1件につき利用者1人。**
- UIDごとに `privateDuties/{uid}/shifts/{shiftId}` の原本を分離し、現在の操作端末・閲覧専用端末を区別する。
- 進行中・未同期・送信結果不明・競合の日報がある場合、他人のデータに切り替わる操作で無断上書き・削除しない。管理者権限・本人以外の日報の取得制限を維持。
- 新規登録名は全員に対して一意で、管理者からの名前変更でも同じ一意性を守る。名前の正規化ルールは**実装前に確定**する。

## 今回の画面・動作の実装
- 同じ `index.html` に未ログイン時「Googleでログイン」「新規登録」と説明、ログイン済みは本人Googleメール・UIDおよび登録済みオプチャネーム、別Googleアカウントでログイン／新規登録、ログアウトを表示する。
- 別Googleへの切替では、既存の `beforeSignOut` を通して端末永続保存・Firestore最終同期・競合の照合を行い、保護が必要なら**ログアウトもGoogle選択も始めず停止**する。
- 乗務中（`activeId` が入庫未完了）ならログアウトとアカウント切替を停止する。本人Firestore原本を保持し、入庫・保存確認後に再操作する。
- 入庫済みでもFirestore読戻しによる更新番号・内容の「保存確認済み」が確認できない乗務がローカルに残る場合は、UID切替を止める。閲覧専用端末が未確認原本を持つ場合も保護する。
- 同期待機後のブラウザポップアップブロックを防ぐため、アカウント切替は**①安全なログアウト ②未ログイン画面で新しいGoogleを選択**の2段階とする。
- 登録済みGoogle UIDなら既存 `users/{uid}` を読むだけで、重複作成しない。未登録でGoogleメール認証を通した場合のみ、既存の新規登録処理が登録名を求める。
- 管理者の `users` プロフィールが存在しない場合も、`admins/{uid}.openChatName` の表示名をログイン情報に表示する。
- 他アカウントの原本をローカル画面へ混入させない既存 `switchAccountScope` を維持。管理・印刷の既存機能は変更しない。

## 決定仕様だが未完成：オプチャネーム全員一意性
**現行実装では、UID自身の二重作成を拒否できるが、異なるUIDが同じ／類似のオプチャネームで登録することまでは防げない。**
`firestore.rules` は利用者による `users` 一覧取得を禁止しており、他の登録名をブラウザで検索する回避策は採用しない。画面側だけの照合も同時登録で競合し、決定仕様を満たさない。

### 重複判定の具体案（提案・**未確定**）
1. Unicode **NFKC**（全角英数字／半角カナの表記統一）
2. 名前の前後のUnicode空白を除去、内部の連続空白は半角スペース1個に統一
3. ラテン大文字小文字を区別しない（Unicodeの `toLocaleLowerCase('ja-JP')` 相当）
4. 1〜32文字と制御文字禁止。表示名の原文は保持し、比較用キーを別で管理する
5. 異なる人の同一比較キーは登録・管理者名変更を拒否

この具体案を決定仕様として採用するには**利用者の承認が必要**。既存登録の同名・類似名の棚卸し、重複時の利用者による解決、安全な一意名予約、未同期端末の扱いを先に確定する。

### サーバー保証について
- 新規作成と名前予約を原子的に処理し、**Firestore Security Rulesが検査できる条件**または信頼できるサーバー側で一意性を保証する必要がある。
- 無償Sparkプランでは管理者Cloud Functionsが未配信。名称のNFKC処理をブラウザだけで行う場合、未改造クライアントや同時登録に対する厳格なサーバー保証にはならない。
- 管理者による名前変更も同じ一意名予約経路を通す必要がある。現状のFirebase Consoleからの直接名前変更は、一意予約を介さずに編集できるため、これも**まだ一意保証に含まれない**。
- 既存登録を無断変更・削除したり、過去のオプチャネームを勝手に変更したりしない。

## 本番変更に必要な別途承認と復旧
- 本番 `firestore.rules`、Firebase Authentication権限、新しい一意名予約コレクションへの正式切替、既存登録データの移行／登録名の変更は**別途承認事項**。
- 影響：既存／新規登録の可否、ユーザーと管理者の登録方式、名前変更、端末UID認証、利用者個別データのアクセス制御。
- 対策：ルールの現状保存、合成ユーザーでの同時登録検証、既存名重複の棚卸し（個人情報を公開しない）、段階移行、ロールバック手順を承認前に用意する。
- 復旧：問題時は旧ルールを復元し、新規登録処理だけを停止・保留。既存のUID別原本・端末未同期データ・Google帳票は触れない。

## 2026年10月25日 低頻度のアカウント操作を設定へ移動
- 乗務中の画面最上部に「別のGoogleでログイン」「別のGoogleで新規登録」「PCアカウント管理」「ログアウト」を横並びにすると視認性が悪いとの利用者の指摘を受けて修正。
- **ログイン済みの場合は上部に操作端末の状態・短いアカウント表示だけを残す**。切替・新規登録・ログアウト・PC管理は既存「設定」→「データ・アカウント」→「ログイン中のアカウント情報」へ集約する。
- **未ログインの初回アクセスでは新規登録・ログインのボタンを上部に残す**。初めての利用者が設定を探さなくても登録できる。
- 設定の操作ボタンは既存の認証操作へ委譲するため、従来の `beforeSignOut` による乗務中・未同期日報・送信結果不明・競合の保護を迂回しない。
- 閲覧専用端末でも設定からアカウントの確認と切替操作を呼び出せるよう、ゲートは表示／認証操作に限って許可。原本の編集権限は従来どおり。
- 上部の「この端末で操作する」は日々の運用に必要なため従来どおり表示する。
- 原本、計算、Firestoreルール、本人UID分離、Google帳票、料金プランは変更しない。
